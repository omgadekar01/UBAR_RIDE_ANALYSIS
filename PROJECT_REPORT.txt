1. ABSTRACT
-----------
This project presents an interactive dashboard for inspecting ride pickup
records and demonstrating a basic hourly-demand prediction workflow. The
application is written in Python and uses Pandas and NumPy for data
processing, Plotly for interactive visualizations, Scikit-learn for a
Random Forest regression model, and Streamlit for the user interface.

The dashboard loads the supplied CSV by default or accepts another CSV
through a sidebar uploader. It reports data quality, removes exact
duplicate records, converts a detected pickup timestamp to datetime, and
excludes records with missing or invalid pickup timestamps from
time-based analysis. It displays daily, daytime hourly, and weekday pickup
summaries; a correlation heatmap for eligible numerical measurements; and
an hourly-demand model evaluated on a chronological holdout period.

On the supplied file, the Random Forest did not outperform the
training-mean baseline. The measured negative R-squared indicates that
the predictions did not explain variation in the held-out hourly counts
better than the mean reference. The project is therefore an educational
analytics demonstration, not a claim of accurate operational forecasting.


2. INTRODUCTION
---------------
Ride records contain timestamps and may also contain locations, trip
distances, fares, statuses, and identifiers. Summarizing such records by
date, hour, or weekday can help a user explore when pickups were recorded.
However, raw CSV data can contain duplicate rows, invalid dates, missing
values, or column names that differ between datasets.

This project places the data preparation, visual analysis, correlation
analysis, and a simple predictive experiment in one Streamlit dashboard.
The user can inspect the input, see the cleaning effects, filter the
pickup-date interval, and compare model predictions with actual counts.


3. PROBLEM STATEMENT
--------------------
It is inconvenient to inspect a large ride CSV manually and difficult to
compare ride volume across time without grouping and visualization. A
beginner-friendly application is needed to load ride data, identify a
pickup-time field, report data quality, show useful time summaries, and
demonstrate a reproducible prediction evaluation without inventing fields
or claiming unsupported model accuracy.


4. AIM AND OBJECTIVES
---------------------
Aim:
Build an interactive analytics dashboard for ride pickup records and
evaluate a simple model for hourly record-count prediction.

Objectives:
1. Load the provided CSV or a user-uploaded CSV file.
2. Display the input dimensions, sample rows, column types, missing
   values, and duplicate count.
3. Identify a supported pickup timestamp column without requiring the
   user to rename the supplied columns.
4. Remove exact duplicate rows and records with unusable pickup
   timestamps, and report the before-and-after row counts.
5. Visualize daily, hourly, and weekday pickup-record counts.
6. Calculate numerical correlations while excluding identifier-like
   fields from the continuous-measurement analysis.
7. Aggregate records into hourly counts and create calendar/time-index
   features.
8. Evaluate a Random Forest with an earlier-to-later chronological split
   and compare it with a training-mean baseline.
9. Provide a download of the cleaned CSV.

8. METHODOLOGY
--------------
8.1 CSV loading
The application first reads a user-uploaded CSV if one is selected.
Otherwise, it loads the supplied project CSV. Empty or unreadable files
and files without a recognizable pickup timestamp produce an explanatory
message instead of model results.

8.2 Column detection
The application recognizes common timestamp headers, including
pickup_time, pickup_datetime, pickup_date, Date/Time, datetime, and
timestamp, with additional pickup/date/time name matching. This supports
common dataset variations but cannot guarantee recognition of every
possible custom header.

8.3 Cleaning
The application:
1. Counts exact duplicate rows.
2. Removes those exact duplicate rows.
3. Converts the detected pickup timestamp to a datetime value, coercing
   unparseable values to missing datetimes.
4. Counts and removes rows whose pickup timestamp is missing or invalid.
5. Reports, but does not guess replacements for, missing values in
   other columns.

8.4 Exploratory analysis
For the selected date interval, the application counts pickup records
per calendar day, hour of day (0 to 23), and weekday (Monday to Sunday).

8.5 Correlation analysis
The heatmap uses numeric columns that vary and are not named like IDs.
For the supplied CSV, the selected fields are pickup_lat, pickup_lng,
drop_lat, drop_lng, distance_km, and fare_amount. Correlation describes
association and does not prove that one variable causes another.

8.6 Hourly demand and predictive model
Each retained row is counted in its pickup hour. Empty hours between the
first and last pickup are included as zero-count hours. Model inputs are:
- hour of day
- day of week
- month
- weekend indicator
- sequential time index

The first 80 percent of hourly buckets, in time order, are used for
training. The final 20 percent are held out for testing. A
RandomForestRegressor with 150 trees, minimum leaf size 2, and random
seed 42 is fitted to the training period. Its predictions are compared
with a baseline that predicts the mean training-period count for each
test hour.

Metrics:
- MAE (Mean Absolute Error): mean absolute prediction error in rides
  per hour; lower is better.
- RMSE (Root Mean Squared Error): error in rides per hour that penalizes
  larger misses more; lower is better.
- R-squared: comparison with a mean-only reference on the test data.
  A negative value means the evaluated predictions are worse than the
  test-set mean reference under this metric. R-squared is omitted when
  the test target cannot support a meaningful calculation.

10. DASHBOARD MODULES
---------------------
10.1 Overview
Shows pickup-record, active-day, and average-record-per-active-day KPI
cards; a pickup date filter; and daily, daytime hourly, and weekday charts.
The hourly chart displays 6:00 AM–5:59 PM only; nighttime pickups remain
included in the other dashboard analysis. Charts
use concise titles, a consistent color palette, and minimal gridlines for
clarity.

10.2 Correlation Analysis
Displays an interactive numerical correlation heatmap and a reminder
that correlation does not establish cause and effect. The heatmap uses a
simple diverging color scale and displays the correlation values.

10.3 Predictive Model
Displays the number of hourly buckets used for training and testing,
Random Forest and baseline metrics, actual-versus-predicted values, and
feature importance in simplified charts. Results correspond to the
currently selected date interval.

10.4 Data Quality
Displays all uploaded source rows in a scrollable table, row and column information, data types,
missing values before and after cleaning, duplicate and invalid-time
counts, cleaned row count, and a cleaned-data preview.

13. LIMITATIONS
---------------
1. The source/provenance of the supplied CSV is not stated in the project
   files. Cite the original data source if it is known.
2. The model uses only calendar fields and a sequential time index; it
   does not use weather, holidays, special events, traffic, or service
   disruptions.
3. The hourly series in the supplied data is almost constant, so the
   example provides a weak forecasting challenge and the model does not
   beat the mean baseline.
4. The model counts all retained rows regardless of status. Counts are
   pickup-record counts, not necessarily completed rides.
5. A chronological split tests one historical period and does not
   guarantee future performance.
6. Feature importance is not a causal explanation.
7. The app removes exact duplicates only. It does not determine whether
   two non-identical rows describe the same real-world ride.
8. Missing non-timestamp fields are reported, not imputed.
9. Column-name detection supports common aliases but not every possible
   custom naming convention.
10. The date-range filter affects overview and model results. The
    correlation and data-quality tabs describe the full cleaned upload.

15. CONCLUSION
--------------
The project delivers a working Streamlit dashboard for CSV loading,
quality reporting, pickup-time exploration, numerical correlation, and
hourly demand-model evaluation. It handles the supplied dataset without
requiring column renaming and offers support for common timestamp headers. The evaluation is transparent:
on the included data, the Random Forest did not outperform the simple
training-mean baseline. This is a useful outcome because it demonstrates
why models should be compared with baselines and why measured results
should be reported honestly.
